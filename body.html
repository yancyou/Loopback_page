Loopback Transformer: Towards a Unified View of Residual Looped Transformers

Xuan Ouyang1 Zefan Cai1 Chenlong Zhang2 Cheng Luo3 Ke Wan4 Junjie Hu1
1UW–Madison 2UC Santa Barbara 3Caltech 4Microsoft
Paper Code

The arXiv and code links go live at release.

Three ways a looped stack reuses its updates. (a) Ordinary addition carries every update with weight one. (b) An explicit depth history reads the input and earlier updates with learned coefficients. (c) Hyper-connection families carry several memory streams. All three are instances of one write–transport–read interface; Loopback is the instance that stores updates, keeps the input on its own path, and lets decay set the total weight that attention allocates.

Abstract

Looped Transformers reduce parameter count by repeatedly applying shared blocks, but parameter sharing alone does not determine how the results of repeated computation are reused. Building on the depth-memory view of residual connections, we analyze how the written representation and weighting rule constrain the contribution of each update. Storing a full block output also writes back its input, changing how earlier information is carried forward. Reading individual updates with a separate input path exposes independent controls over input strength, total update weight, and allocation. Guided by this analysis, we develop the Loopback Transformer, which stores individual block updates and keeps the shared stack's input on a separate path. Geometric decay controls total update weight and supplies a recency prior, while attention learns how to allocate that weight. On ClimbMix, Loopback uses only about 40% and 58% of the dense controls' Transformer parameters at the 191M and 374M scales, respectively, while achieving lower validation loss and better downstream performance at the studied training budgets; the advantage persists at 778M and 1.4B with about two thirds of the parameters. Comparisons use the same training-token budget and computational depth within each scale.

Method Overview

1. One interface for residual rules: addition, Attention Residuals, Hyper-Connections, mHC, Hyperloop and recurrent depth readers all write a value, carry old memory forward, and read it to form the next hidden state. Unrolling the interface gives every earlier update an explicit coefficient, which exposes two couplings: storing a full block output also rewrites the input it contains, and a joint softmax over the input and the updates ties their weights to a single unit.

2. Store updates, keep the input on its own path, set the total with decay: Loopback appends each block's update δ rather than its output and keeps the shared stack's input at coefficient one. At every visit end a geometric factor λ shrinks all stored weights, so the prior favors recent visits and the total update weight stays bounded by Kλ/(1−λ).

3. Attention allocates the total: a destination query scores the normalized updates and redistributes the decay-set total across them. Zero queries recover the decay-only loop exactly; λ = 1 with zero queries recovers ordinary addition. A fused Triton kernel streams the stored updates once per read.

Loopback on a two-visit loop. (a) Each shared-block application appends its update and reads the history. (b) Decay sets the prior and the total weight. (c) Attention reallocates the total across the raw updates; the input enters with coefficient one and is not decayed again before the coda.

Results

On ClimbMix, Loopback reaches lower validation loss and higher zero-shot accuracy than matched-depth dense controls at 191M, 374M, 778M and 1.4B, with 40–68% of their Transformer parameters. Every comparison matches training tokens and executed depth; parameter counts exclude embeddings and the vocabulary head.

Parameter efficiency at 191M and 374M

Training loss at four scales

100-step moving averages against tokens seen. The final training-loss gap to Dense is −0.005, −0.024, −0.019 and −0.021 nats at 191M, 374M, 778M and 1.4B while Loopback stores 40–68% of Dense's Transformer parameters.

Scale-up to 778M and 1.4B

With 67% and 68% of Dense's Transformer parameters, Loopback lowers validation loss by 0.019 and 0.021 nats and raises the seven-task mean by 0.90 and 0.87 points (47.83→48.73 and 52.11→52.98); the thirteen-task mean and WikiText perplexity improve as well.

Linear attention and recurrent memory along depth

Eleven recurrent and linear-attention cores (linear attention, RetNet, GLA, Mamba-2, HGRN-2, DeltaNet, Gated DeltaNet, KDA, RWKV-7, Mesa and a LaCT-inspired reader) adapted to read the loop's history. All of them improve on the plain loop, reading updates beats reading cumulative states in every family at both scales, and none reaches Loopback: deltas are a useful starting point, not a complete residual design.

Decay and attention

Toggling the two components. Decay supplies most of the gain over the plain loop; learned allocation adds a further improvement at both scales. At 191M, uniform allocation at decay's total weight recovers 78% of decay's gain, versus 20% for its recency profile at the plain total.

Compute and efficiency

All models execute the same blocks per token, so the read adds under 0.1% to forward FLOPs. It adds memory traffic: with the fused Triton kernel the step-time overhead is 33% at 191M and 19% at 778M. The KV cache equals Dense's; stored weights are 29–45% smaller (0.20 vs 0.36 GiB at 191M, 1.87 vs 2.64 GiB at 1.4B in bf16).
